You are designing and implementing the AI subsystem of a serious long-term coding apprenticeship platform.

IMPORTANT:
Do NOT redesign the application UI, notification system, general product architecture, or curriculum content itself unless required to define an interface with this AI subsystem.

Your task is to deeply design the AI subsystem that powers a persistent coding tutor.

This is NOT a chatbot.

The system must behave like a persistent human-like tutor who teaches one learner every day through a structured curriculum, remembers previous sessions, continuously evaluates the learner, asks questions during teaching, diagnoses why the learner is struggling, adapts how it teaches, handles clarification and real-world circumstances, and carries the learning state forward from one day to the next.

The AI itself is fallible. The architecture must therefore support uncertainty, clarification, correction, historical reasoning, and revision of previous tutor decisions.

Do not simplify this into:
    user message -> LLM -> response

That architecture is explicitly insufficient.

============================================================
1. CORE OBJECTIVE
============================================================

Build an AI subsystem that can continuously perform this loop:

    determine what the learner should learn
    -> inspect what the learner currently understands
    -> teach
    -> ask questions
    -> observe answers and behavior
    -> form hypotheses about understanding/problems
    -> clarify ambiguous situations with the learner
    -> choose a teaching intervention
    -> observe whether it worked
    -> update learner state
    -> update tutor knowledge about what worked
    -> determine what should happen next
    -> produce a persistent session report
    -> use that report in future sessions

The tutor must preserve continuity across many sessions.

The tutor must know:
    what was planned
    what actually happened
    what was learned
    what was not learned
    what misconceptions appeared
    what questions the learner asked
    what teaching methods worked
    what teaching methods failed
    what the tutor previously believed
    whether previous tutor beliefs were later proven wrong
    what should happen next
    where the learner currently sits in the curriculum

============================================================
2. FUNDAMENTAL DESIGN PRINCIPLES
============================================================

Treat the LLM as a probabilistic reasoning component, NOT as the source of truth.

The system owns:
    application state
    curriculum state
    session state
    historical records
    content approval state
    provider state
    quota state
    execution results
    learner evidence

The LLM provides:
    interpretation
    reasoning
    pedagogical decisions
    natural-language teaching
    content generation
    hypothesis generation
    diagnosis
    adaptation

Never allow an LLM response to silently become authoritative system state.

Every important AI interpretation must be distinguishable from the underlying evidence.

For example:

FACT:
    learner omitted a semicolon five times

INTERPRETATION:
    learner may have a syntax weakness

ALTERNATIVE:
    learner may have an input-device problem

LEARNER CONTEXT:
    learner says their semicolon key intermittently fails

DECISION:
    do not count those syntax errors as strong evidence of C++ weakness

OUTCOME:
    later syntax performance is normal

The system must preserve these distinctions.

6. PROVIDER QUOTA AND RATE LIMIT MANAGEMENT
============================================================

This is a first-class subsystem.

Track independently:
    requests per minute
    tokens per minute
    requests per day
    tokens per day
    monthly limits
    spending limits
    provider-specific quotas

Distinguish:

RATE_LIMIT:
    temporary capacity problem

DAILY_QUOTA_EXHAUSTED:
    provider cannot be used until reset

PROVIDER_FAILURE:
    service failure

MODEL_UNAVAILABLE:
    specific model unavailable

INVALID_REQUEST:
    do not retry blindly

Quota must be reservable atomically.

Example:
    background generation must not consume the final AI capacity needed by a learner currently in an active session.

Define request priorities.

Recommended priority classes:

    P0 = learner currently waiting for tutor response
    P1 = active session critical work
    P2 = preparation for upcoming session
    P3 = background content generation
    P4 = optimization / regeneration / experiments

P3/P4 work must be preemptible or deferrable.

Never let background jobs exhaust capacity reserved for P0/P1.

10. C. CONTENT GENERATION SYSTEM
============================================================

Content generation is different from live tutoring.

Live tutoring is:
    dynamic
    contextual
    low latency
    usually ephemeral

Content generation is:
    reusable
    persistent
    expensive
    validated
    versioned

Never automatically publish generated content.

Pipeline:

    content requirement
    -> search approved content
    -> if suitable content exists, reuse it
    -> otherwise queue generation
    -> generate candidate
    -> schema validation
    -> deterministic validation
    -> AI semantic review
    -> repair if necessary
    -> final validation
    -> approve
    -> persist
    -> make available to tutor

============================================================
11. CONTENT GENERATION MUST BE NEED-DRIVEN
============================================================

Do not generate arbitrary educational material.

A generation request must have:

    concept
    learning objective
    learner level
    prerequisites

    desired resource type
    difficulty
    expected duration
    curriculum context
    known learner weaknesses if relevant

Example:

    learner has weak understanding of object lifetime
    tomorrow requires RAII

    generate targeted object-lifetime remediation resource

This is better than:

    generate lesson about object lifetime

24. G. TUTOR REASONING ENGINE
============================================================

This is the core component.

The tutor must operate as a reasoning loop.

The loop is:

    observe
    -> extract evidence
    -> identify possible interpretations
    -> check existing learner state
    -> generate hypotheses
    -> identify uncertainty
    -> determine whether clarification is needed
    -> ask learner if necessary
    -> interpret learner response
    -> revise hypotheses
    -> choose intervention
    -> teach
    -> observe outcome
    -> evaluate intervention
    -> update learner model
    -> update tutor experience
    -> choose next action

Do NOT implement:

    user message
    -> LLM
    -> answer

as the primary architecture.

============================================================
25. FACT VS INTERPRETATION
============================================================

The tutor must explicitly distinguish:

FACT:
    learner made 5 punctuation errors

INTERPRETATION:
    possible syntax weakness

ALTERNATIVE:
    input-device issue

LEARNER CONTEXT:
    learner reports comma key intermittently fails

CONCLUSION:
    punctuation errors should not currently be used as strong evidence of syntax weakness

This distinction must exist in the internal state model.

============================================================
26. LEARNER CONTEXT CAN CHANGE THE INTERPRETATION
============================================================

Example:

Tutor observes:
    learner repeatedly misses commas.

Initial possible explanation:
    syntax weakness.

Tutor asks:
    "Are you unsure where the punctuation belongs, or is the issue mainly when typing it?"

Learner:
    "My comma key doesn't work properly sometimes."

Tutor must update its interpretation.

It must NOT continue reasoning:

    syntax mistakes
    -> syntax weakness
    -> more syntax teaching

The environmental explanation must be incorporated into current context.

This context may be temporary.

Do not permanently label the learner as having a keyboard problem.

============================================================
27. THE LEARNER IS A SOURCE OF EVIDENCE
============================================================

The learner can provide information unavailable to the system:

    environmental problems
    hardware issues
    intent
    reasoning behind an answer
    misunderstanding of the question
    prior knowledge
    external constraints
    time constraints
    personal context relevant to the session

Learner statements must influence reasoning.

However, learner statements are evidence, not automatically verified truth.

When necessary, verify through another question or observation.

============================================================
28. CLARIFICATION ENGINE
============================================================

When multiple plausible explanations exist, do not blindly choose one.

Determine:

    what information would distinguish the explanations?

Then ask the smallest useful clarification question.

Example:

Possible causes:
    syntax weakness
    typing problem
    rushing

Useful question:
    "When you're reading code, do you know where the punctuation goes, and is the problem mainly when you're typing?"

Do not ask unnecessary chains of questions.

33. ROOT-CAUSE REASONING
============================================================

The tutor must not assume the visible failure is the root cause.

Example:

    learner repeatedly fails binary search

Possible causes:

    indexing
    loops
    sortedness
    search-space reasoning
    invariants
    problem interpretation
    implementation
    complexity understanding

The tutor should investigate before choosing remediation.

If several related concepts fail, investigate shared prerequisites.

Example:

    pointers weak
    references weak
    lifetime weak
    RAII weak

Possible shared cause:

    underlying memory/object model weakness

The tutor should test this possibility.

    self-corrections

36. TUTOR MISTAKES
============================================================

The tutor can make wrong decisions.

This is expected.

Do NOT erase the mistake.

Example:

Initial belief:
    learner has weak recursion understanding

Later evidence:
    learner solves unfamiliar recursion problems correctly

Revision:
    original diagnosis was likely wrong

Store:

    original hypothesis
    evidence
    decision
    outcome
    correction
    new hypothesis

Future tutor reasoning should be able to retrieve this experience.

The system should learn:

    "This pattern previously looked like recursion weakness,
     but that interpretation was incorrect."

============================================================
37. TUTOR SHOULD BE ABLE TO ASK FOR CLARIFICATION
============================================================

If the tutor does not know why something happened, it should ask.

Examples:

    "Was that an intentional choice or did you not know this part?"

    "Did you understand the algorithm but get stuck implementing it?"

    "Are you unsure about the syntax, or is the editor causing the issue?"

    "Do you remember the concept but not how to apply it?"

Do not force the tutor to produce a confident diagnosis when evidence is insufficient.

============================================================
38. TUTOR SHOULD NOT BLINDLY TRUST LEARNER CLAIMS
============================================================

If unsuccessful:
    identify the actual gap

If learner says:
    "I don't understand anything."

The tutor should identify what specifically is unclear.

49. MEMORY AUTHORITY
============================================================

    application state and verified execution results
    > approved curriculum
    > verified historical records

    > tutor hypotheses
    > model speculation

However, learner statements can introduce information unavailable elsewhere.

Therefore learner statements should be treated as evidence requiring appropriate verification, not ignored.

============================================================
50. K. AI CONTENT + LIVE TUTOR SEPARATION
============================================================

Do not confuse these.

CONTENT GENERATION:
    creates reusable assets
    can run asynchronously
    can wait for quota
    requires validation
    persists approved output

LIVE TUTOR:
    learner is waiting
    low latency
    high priority
    must work even if background generation is unavailable
    should reuse approved content whenever possible

Background generation must never starve live tutoring.

============================================================
51. LIVE TUTOR DEGRADATION
============================================================

If AI providers fail:

    first use another capable provider
    then use approved existing content
    then use prepared hints/examples/explanations
    then preserve session state and degrade gracefully

Never lose learner progress because of provider failure.

============================================================
52. CONTENT RETRIEVAL BEFORE GENERATION
============================================================

Whenever tutor needs:

    explanation
    example
    exercise
    hint
    remediation

first check approved content.

Only generate new content if existing content is insufficient.

This is critical for:

    cost
    quota
    latency
    consistency
    reliability

53. L. QUALITY / EVALUATION

Evaluate the tutor itself.

    missed remediation
    intervention effectiveness
    learner independence

    repeated misconception rate

Do not measure only:

54. TUTOR DECISION AUDITING

    later evaluation

============================================================
55. HIGH-RISK VS LOW-RISK AI DECISIONS
============================================================

Do not spend expensive reasoning on everything.

LOW RISK:
    wording of simple explanation
    simple example

MEDIUM:
    teaching strategy
    diagnosis of a local mistake

HIGH:
    changing curriculum direction
    skipping prerequisites
    declaring mastery
    significant remediation
    changing long-term learner model

Higher-risk decisions require stronger evidence and potentially additional verification.

============================================================
56. IMPORTANT ANTI-PATTERNS
============================================================

Do NOT implement any of the following:

1. One giant tutor prompt containing the entire learner history.

2. Direct provider calls from tutor code.

3. One global mastery score.

4. Automatically treating every mistake as evidence of lack of knowledge.

5. Automatically trusting every learner statement.

6. Automatically distrusting learner statements.

7. Generating new content whenever the tutor needs something.

8. Publishing AI-generated content without validation.

9. Using one model as generator, judge, and unquestioned authority for all high-risk content.

10. Allowing background AI jobs to consume all quota.

11. Treating raw chat history as the only memory.

12. Silently overwriting incorrect tutor decisions.

13. Letting the LLM directly mutate authoritative curriculum state.

14. Assuming the learner's current problem is always the root cause.

15. Repeating the same teaching strategy after evidence shows it is ineffective.

16. Asking questions merely to make the conversation look human.

17. Advancing curriculum simply because the learner passed one exercise.

18. Reverting curriculum simply because the learner failed one exercise.

19. Treating temporary environmental issues as permanent learner traits.

20. Making the tutor provider-dependent.

58. EXPECTED REAL-LIFE BEHAVIOR
============================================================

The implementation must support scenarios such as:

SCENARIO A:

Tutor notices repeated punctuation errors.

Tutor does NOT immediately conclude:
    syntax weakness.

Tutor asks for clarification.

Learner explains:
    keyboard key intermittently fails.

Tutor updates context.

Those errors are not treated as strong learning evidence.

------------------------------------------------------------

SCENARIO B:

Learner says:
    "I already know recursion."

Tutor verifies with a transfer/diagnostic question.

Learner succeeds.

Tutor reduces introductory explanation.

------------------------------------------------------------

SCENARIO C:

Learner says:
    "I don't understand recursion."

Tutor asks what specifically is unclear.

Learner explains:
    "I understand what recursion is, but I don't understand
     what happens to previous calls."

Tutor identifies:
    call-stack mental model issue.

Tutor changes teaching strategy to stack tracing.

------------------------------------------------------------

SCENARIO D:

Learner repeatedly fails several apparently different concepts.

Tutor detects a shared prerequisite.

Instead of teaching each failed concept independently,
the tutor investigates the underlying prerequisite.

------------------------------------------------------------

SCENARIO E:

Tutor previously diagnosed a concept weakness incorrectly.

Later evidence proves the diagnosis wrong.

The system records the correction.

Future tutor reasoning can retrieve that experience.

------------------------------------------------------------

SCENARIO F:

Primary AI provider reaches daily quota during an active session.

Background content generation is paused.

A fallback model handles the live tutor.

Prepared approved content remains available.

The session continues.

------------------------------------------------------------

SCENARIO G:

Learner asks:
    "What did we do on August 5?"

The tutor retrieves the actual historical session,
summarizes it,
and does not invent information.

------------------------------------------------------------

SCENARIO H:

Learner asks:
    "Why are we doing this today?"

Tutor explains using:
    curriculum state
    previous session report
    current weakness
    planned progression

The answer should have a real reason.

============================================================
59. IMPLEMENTATION PHILOSOPHY
============================================================

Build the subsystem as a closed-loop reasoning system.

The fundamental data flow is:

    FACT
    -> INTERPRETATION
    -> HYPOTHESIS
    -> CLARIFICATION
    -> DECISION
    -> ACTION
    -> OUTCOME
    -> RE-EVALUATION
    -> UPDATED STATE

The system must preserve each stage.

Do not collapse them into one LLM response.

The tutor must be able to say, internally:

    "I observed X."

    "I initially thought Y."

    "The learner told me Z."

    "That makes Y less likely."

    "I need one more piece of evidence."

    "I will test it using this question."

    "The learner's response supports hypothesis A."

    "I will use intervention B."

    "The intervention did not work."

    "Therefore my previous diagnosis or teaching strategy may have
     been wrong."

    "I will change approach."

That is the intended intelligence model.

62. FINAL DESIGN TEST
============================================================

Before considering the AI subsystem correctly designed, prove that the architecture can handle this complete sequence:

Day 1:
    tutor begins teaching.

During teaching:
    tutor asks questions.
    learner answers.
    tutor updates understanding.

Learner gets stuck:
    tutor diagnoses rather than immediately giving an answer.

Tutor sees repeated mistakes:
    tutor forms multiple possible explanations.

Learner provides additional context:
    tutor changes its interpretation.

Tutor tries an intervention:
    intervention fails.

Tutor recognizes failure:
    changes strategy.

Session ends:
    system records what happened,
    what was learned,
    what remains uncertain,
    what the tutor got wrong,
    and what should happen next.

Day 2:
    tutor retrieves yesterday's report.

Tutor asks learner what they remember.

Learner partially remembers.

Tutor identifies the exact retained/missing pieces.

Tutor connects today's lesson to yesterday's lesson.

During today's lesson:
    learner asks a historical question.

Tutor retrieves the relevant historical event.

Learner claims:
    "We already learned this."

Tutor checks history and determines:
    related concept was learned,
    but this exact concept was not.

Tutor explains why the current topic is different.

Later:
    provider quota is exhausted.

System switches provider.

Background generation is paused.

Live tutoring continues.

Weeks later:
    a previous tutor diagnosis is discovered to have been wrong.

System preserves the original decision,
records the correction,
and allows future reasoning to use that experience.

If the architecture cannot support this sequence cleanly,
the architecture is incomplete.

63. FINAL REQUIREMENT
============================================================

Think of this system as:

    a persistent reasoning tutor
    operating over a long-running learner relationship,
    using AI as one reasoning component,
    backed by persistent memory,
    curriculum state,
    evidence,
    verification,
    content,
    provider infrastructure,
    and feedback.

Do not optimize for making the chatbot sound human.

Optimize for making the tutoring process behave intelligently.

The final system should be able to distinguish:

    what happened

    what it thinks happened

and distinguish:

    what the learner said
    from
    what the system verified

and distinguish:

    what the tutor currently believes
    from
    what is actually known

and distinguish:

    what the tutor planned
    from
    what actually happened

and distinguish:

    a learner problem
    from
    an environmental problem

and distinguish:

    a local failure
    from
    a root learning problem

and distinguish:

    temporary confusion
    from
    persistent misconception

and distinguish:

    recognition
    from
    understanding

and distinguish:

    understanding
    from
    independent application

and distinguish:

    immediate success
    from
    retained learning.

This distinction is the foundation of the entire AI subsystem.
